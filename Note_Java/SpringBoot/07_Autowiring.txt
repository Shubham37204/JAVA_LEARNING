### What is Autowiring?

**Autowiring means Spring automatically provides the required dependency to a class.**

For example, `UserService` needs `UserDao`:


@Component
public class UserService {

    @Autowired
    private UserDao dao;
}

---

# 3 places where `@Autowired` can be used

## 1. Setter Method Injection

private PwdService pwdService;

@Autowired
public void setPwdService(PwdService pwdService) {
    this.pwdService = pwdService;
}

Spring calls the setter method and **passes the required Bean**.

Think in Core Java terms:

UserService service = new UserService();

service.setPwdService(pwdServiceObject);

The difference is that **Spring performs this automatically**.

You can have multiple setter injections:

@Autowired
public void setPwdService(PwdService pwdService) {
    this.pwdService = pwdService;
}

@Autowired
public void setUserDao(IUserDao userDao) {
    this.userDao = userDao;
}

@Autowired
public void setEmailService(EmailService emailService) {
    this.emailService = emailService;
}

---

# 2. Constructor Injection

Conceptually:

@Component
public class UserService {

    private PwdService pwdService;
    private IUserDao userDao;

    @Autowired
    public UserService(PwdService pwdService, IUserDao userDao) {
        this.pwdService = pwdService;
        this.userDao = userDao;
    }
}


Here Spring provides the required Beans **through the constructor**.

Think in Core Java:

UserService service =
    new UserService(pwdServiceObject, userDaoObject);

Spring automatically supplies those objects.

**Important:** In modern Spring, if there is only **one constructor**, `@Autowired` is generally not required.

---

# 3. Field Injection

@Component
public class UserService {

    @Autowired
    private PwdService pwdService;

    @Autowired
    private IUserDao userDao;

    @Autowired
    private EmailService emailService;
}


Here Spring directly injects the required objects into the fields.

So:

UserService
   │
   ├── pwdService  ← Spring injects PwdService
   │
   ├── userDao     ← Spring injects IUserDao
   │
   └── emailService ← Spring injects EmailService


This is called **field injection**.

You may hear that Spring uses **reflection** internally for field injection. For now, just remember:

> **Spring injects the dependency directly into the field.**

---

# Simple comparison

| Injection       | Where `@Autowired` is placed | How dependency comes |
| --------------- | ---------------------------- | -------------------- |
| **Setter**      | Setter method                | Through setter       |
| **Constructor** | Constructor                  | Through constructor  |
| **Field**       | Field                        | Directly into field  |

### Interview answer

> **Autowiring is the process by which Spring automatically provides the required dependency to a Bean. `@Autowired` can be used for constructor, setter-method, and field injection.**

========================================================

@Service
public class UserService {

	@Autowired
	private PwdService pwdService;

	@Autowired
	private IUserDao userDao;

	@Autowired
	private EmailService emailService;

	public void registerUser(String name, String email, String pwd) {

		// encrypt pwd
		String encryptPwd = pwdService.encryptPwd(pwd);

		// save user in db
		boolean isSaved = userDao.saveUser(name, email, encryptPwd);

		// send email
		if (isSaved) {
			boolean isSent = emailService.sendEmail(email, "Test Subject", "Test Body");
			if (isSent) {
				System.out.println("User Registration Completed...");
			}
		}
	}

}

Note:

1. No constructor + Setter Injection

If you don't write any constructor, Java provides a default no-argument constructor.

If the setter is marked with @Autowired, Spring injects the dependency through the setter.

@Component
class Alien {

    private Laptop laptop;

    @Autowired
    public void setLaptop(Laptop laptop) {
        this.laptop = laptop;
    }
}

Spring does roughly:

Alien alien = new Alien();       // 0-arg constructor
alien.setLaptop(laptop);         // setter injection

Remember: No constructor + @Autowired setter → setter injection.

2. 0-argument constructor + parameterized constructor + @Autowired

Suppose we have:

@Component
class Alien {

    private Laptop laptop;

    public Alien() {
        System.out.println("0-arg constructor");
    }

    @Autowired
    public Alien(Laptop laptop) {
        System.out.println("parameterized constructor");
        this.laptop = laptop;
    }
}

Because the parameterized constructor is marked @Autowired, Spring uses it for dependency injection.

@Autowired constructor
        ↓
Spring finds Laptop
        ↓
Alien(Laptop laptop)

So @Autowired tells Spring which constructor to use for injection.

3. Only parameterized constructor + NO @Autowired

This is an important Spring Boot feature.

@Component
class Alien {

    private Laptop laptop;

    public Alien(Laptop laptop) {
        this.laptop = laptop;
    }
}

If this is the only constructor, modern Spring/Spring Boot can use it automatically.

You don't need:

@Autowired

Spring sees:

Only one constructor
       ↓
Use that constructor
       ↓
Inject Laptop

Ambiguity Case:

Yes. In Spring Boot, @Component vs @Component("oracle") becomes especially important when ambiguity occurs during dependency injection.

Let's understand it step-by-step.

1. Suppose we have two classes
@Component
public class Oracle implements DataSource {
}
@Component
public class MySQL implements DataSource {
}

Spring Boot sees:

DataSource
   ↑
   ├── Oracle
   └── MySQL

So Spring has two beans of type DataSource.

Now suppose:

@Component
public class Service {

    @Autowired
    private DataSource dataSource;
}

Spring asks:

"I need a DataSource. Which bean should I inject?"

It finds:

Oracle
MySQL

Both are DataSource.

Therefore Spring cannot decide.

❌ Ambiguity occurs

You typically get an error like:

NoUniqueBeanDefinitionException:
expected single matching bean but found 2
2. Then what does @Component("oracle") do?

You could write:

@Component("oracle")
public class Oracle implements DataSource {
}

and:

@Component("mysql")
public class MySQL implements DataSource {
}

Now the beans have names:

oracle → Oracle object
mysql  → MySQL object

But ambiguity still exists!

If you do:

@Autowired
private DataSource dataSource;

Spring still sees:

DataSource
   ├── oracle
   └── mysql

So bean naming by itself does not solve type-based ambiguity.

3. How do we solve the ambiguity?
Option 1 — @Qualifier

Tell Spring exactly which bean you want:

@Autowired
@Qualifier("oracle")
private DataSource dataSource;

Now Spring says:

I need a DataSource, and specifically the bean named oracle.

So:

DataSource
   ├── oracle ← ✅ SELECT THIS
   └── mysql
Option 2 — @Primary

You can tell Spring:

"If there are multiple beans, prefer this one."

@Component
@Primary
public class Oracle implements DataSource {
}

Then:

@Autowired
private DataSource dataSource;

Spring sees:

DataSource
   ├── Oracle ← ⭐ @Primary
   └── MySQL

So Oracle gets injected.
